# ADR-003: Implement Provider Abstraction for All External Services

**Status:** Accepted

**Date:** 2026-08-14

**Authors:** SolaraSphere Engineering

---

## Context

Radio Atlas depends heavily on external services.

Examples include:

| Provider Category | Examples |
| --- | --- |
| Solar weather | NOAA |
| Radio observations | PSK Reporter |
| Callsign metadata | QRZ |
| Propagation forecasting | VOACAP |
| Satellite data | N2YO |
| Parks activations | POTA |
| AI services | OpenAI |
| Future observation sources | WSPR, Reverse Beacon Network |

Every external provider exposes:

* Different APIs
* Different authentication methods
* Different rate limits
* Different data structures
* Different update frequencies
* Different reliability characteristics

Directly coupling application logic to individual providers creates several risks:

* Vendor lock-in
* Reduced testability
* Difficult maintenance
* Increased implementation complexity
* Reduced extensibility

The competitive analysis revealed that one of Radio Atlas's primary differentiators is its ability to combine multiple independent data sources into a unified radio-weather model.

This requirement makes provider abstraction an architectural necessity rather than an implementation preference.

---

## Decision

All external dependencies shall be accessed through internal provider interfaces.

Application code shall communicate only with provider contracts.

Application code shall never communicate directly with third-party APIs.

---


## Alternatives Considered

### Option 1: Direct Provider Integration

Allow application services to communicate directly with third-party APIs.

#### Advantages

* Faster initial development
* Fewer abstraction layers
* Lower short-term complexity

#### Disadvantages

* Tight coupling
* Difficult testing
* Provider-specific code scattered throughout the application
* Difficult migration
* Significant refactoring required when changing providers

---

### Option 2: Provider Abstraction (Selected)

Implement adapters that expose a standardized internal interface.

#### Advantages

* Loose coupling
* Better testability
* Improved maintainability
* Easier provider replacement
* Simpler mocking
* Better separation of concerns

#### Disadvantages

* Additional abstraction
* More initial implementation work

---

### Option 3: Plugin Architecture

Implement a fully dynamic plugin system.

#### Advantages

* Maximum extensibility
* Third-party plugin support

#### Disadvantages

* Significantly more complexity
* Unnecessary for Version 1.0

---

## Rationale

Radio Atlas is intentionally designed as a **radio observatory rather than a traditional logging application.**

The platform's value comes from combining information from multiple sources and presenting it through a unified visualization layer.

The architecture should prioritize:

* Extensibility
* Interchangeability
* Testability
* Long-term maintainability

Provider abstraction also enables experimentation.

For example:

The forecasting engine could begin with:

```text
ObservedTrendProvider
```

Later, it could incorporate:

```text
VOACAPProvider
```

And eventually:

```text
MachineLearningForecastProvider
```

Without modifying the user interface or domain services.

The same principle applies to AI.

The application should be able to replace:

```text
OpenAIAdapter
```

with:

```text
LocalLLMAdapter
```

without rewriting business logic.

---

## Consequences

### Positive Consequences

* Reduced coupling
* Easier testing
* Easier mocking
* Simpler future migrations
* Greater architectural flexibility
* Easier experimentation

---

### Negative Consequences

* Additional implementation effort
* More interfaces to maintain
* Slightly more architectural complexity

## Testing Implications

Every provider shall support:

* Unit tests
* Mock providers
* Contract tests
* Integration tests

Continuous integration shall never depend on live external APIs.

Mock adapters shall be used during automated testing.
