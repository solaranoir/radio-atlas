# ADR-002: Adopt a Local-First Architecture for Personal QSO Storage

**Status:** Accepted

**Date:** 2026-08-14

**Authors:** SolaraSphere Engineering

---

## Context

Radio Atlas integrates two fundamentally different categories of data:

### Global Observational Data

Examples include:

- PSK Reporter spots
- Solar weather observations
- Gray-line calculations
- Forecasting models
- Anomaly detection
- Historical propagation archives

This information is public, highly dynamic, and shared among all users.

---

### Personal Operating Data

Examples include:

- ADIF files
- Personal contacts
- QSO history
- Achievement progress
- Operating statistics
- Saved filters
- User preferences

This information is private and specific to an individual operator.

---

Traditional amateur radio software generally stores personal contacts locally.

Modern web applications frequently synchronize all user data to the cloud.

Both approaches introduce trade-offs.

The project must satisfy the following requirements:

| Requirement | Priority |
| --- | --- |
| User privacy | High |
| Fast contact analysis | High |
| Historical replay | High |
| Minimal infrastructure costs | High |
| Offline analysis | Medium |
| Synchronization across devices | Medium |
| Scalability | Medium |
| Portfolio demonstration value | High |

---

## Decision

Radio Atlas will adopt a **local-first architecture for personal operating data.**

Personal QSO data will remain on the user's device by default.

Global observations will continue to be stored and processed through shared backend services.

Cloud synchronization will remain optional.

The architecture will separate data into two categories:

```text
                    GLOBAL DATA

              NOAA
              PSK Reporter
              Forecast Models
              Historical Archives

                        │
                        ▼

                    Backend APIs

                        │
                        ▼

                    PostgreSQL

──────────────────────────────────────────────────

                   PERSONAL DATA

                     ADIF Import

                        │
                        ▼

                    Browser Parser

                        │
                        ▼

                     IndexedDB

                        │
         ┌──────────────┼──────────────┐
         ▼              ▼              ▼

   Contact Analysis  Achievements  QSO Story
```

## Alternatives Considered

### Option 1: Fully Cloud-Based Storage

Store all contacts, logs, and operating history in PostgreSQL.

#### Advantages

- Multi-device synchronization
- Centralized backups
- Simpler server-side analytics
- Easier data sharing

#### Disadvantages

- Increased infrastructure costs
- Increased privacy concerns
- Mandatory user accounts
- Larger backend complexity
- Larger database requirements

---

### Option 2: Local-First Storage (Selected)

Store personal QSO data locally using browser-based storage.

#### Advantages

- Better privacy
- Lower infrastructure costs
- Faster local analysis
- Offline functionality
- Optional accounts
- Reduced backend complexity

#### Disadvantages

- More complex browser storage
- Synchronization becomes optional rather than automatic
- Larger frontend responsibility

---

### Option 3: Mandatory Cloud Synchronization

Require authenticated accounts and synchronize all operating data automatically.

#### Advantages

- Consistent user experience
- Built-in synchronization
- Simplified cross-device access

#### Disadvantages

- Conflicts with traditional amateur radio workflows
- Eliminates anonymous usage
- Significantly increases infrastructure requirements

---

## Rationale

The competitive analysis revealed that Radio Atlas should not compete directly with traditional logging software.

The application's primary value lies in:

- Radio-weather visualization
- Historical reconstruction
- Scientific storytelling
- Evidence-based AI
- Propagation analysis

Radio Atlas is **not intended to replace Logbook of The World, N3FJP, DXLab, Ham Radio Deluxe, or other logging applications.**

By treating ADIF files as an importable local resource rather than a cloud-managed dataset, the application can focus on visualization and analysis instead of becoming another full-featured logging platform.

A local-first architecture also reinforces one of the project's strongest differentiators:

**The ability to perform personal analytics without requiring user accounts or cloud synchronization.**

---

## Consequences

### Positive Consequences

- Better user privacy
- Reduced infrastructure costs
- Lower hosting requirements
- Faster local analysis
- Support for offline workflows
- Optional authentication
- Stronger architectural separation

---

### Negative Consequences

- More complex browser storage
- Synchronization requires additional engineering
- Data portability becomes the user's responsibility
- Some cross-device features require optional cloud services

---

## Implementation Notes

### Browser Storage

Use:

- IndexedDB

Store:

- Imported ADIF records
- Achievement state
- Saved filters
- User preferences

---

### Backend Storage

Store:

- NOAA observations
- PSK Reporter spots
- Historical propagation data
- Forecasts
- Anomaly records

---

### Synchronization

Cloud synchronization should remain an optional feature.

Potential future implementations include:

- User accounts
- Cloud backups
- Device synchronization
- Shared operating profiles
