# ADR-008: Adopt a Domain-Driven State Management Architecture

**Status:** Accepted

**Date:** 2026-08-14

**Authors:** SolaraSphere Engineering

---

## Context

Radio Atlas is a highly interactive application.

The system simultaneously manages:

- Live observations
- Historical replay
- Globe interactions
- Forecasting
- AI narratives
- Anomaly detection
- Layer visibility
- User preferences
- Filters
- Animation states

Most traditional amateur radio software uses static views and relatively simple state management.

Radio Atlas introduces a fundamentally different interaction model.

The application must continuously synchronize multiple independent systems while maintaining a responsive user experience.

Examples include:

- Selecting a QSO on the globe
- Opening the QSO Story panel
- Highlighting the selected propagation path
- Updating forecast overlays
- Synchronizing timeline playback
- Replaying historical observations

Without a clear state-management strategy, the application will quickly become difficult to maintain.

---

## Decision

Radio Atlas shall adopt a domain-driven state-management architecture.

State shall be organized according to business domains rather than application layers.

The application shall favor:

- Local component state
- Domain-specific state stores
- Derived state
- Immutable updates

The application shall avoid a monolithic global state store.

## Alternatives Considered

### Option 1: Single Global Store

Use a centralized state-management solution.

Examples:

- Redux
- Large Zustand store

#### Advantages

- Single source of truth
- Centralized state

#### Disadvantages

- Tight coupling
- Reduced maintainability
- Increased complexity
- Difficult debugging

---

### Option 2: Domain-Driven State (Selected)

Separate state into independent domains.

#### Advantages

- Better separation of concerns
- Improved maintainability
- Easier testing
- Better scalability
- Clearer ownership

#### Disadvantages

- More stores to manage
- Additional architectural discipline required

---

### Option 3: Component-Only State

Store all state within React components.

#### Advantages

- Simpler implementation

#### Disadvantages

- Excessive prop drilling
- Poor state sharing
- Difficult synchronization

---

## Rationale

The application's architecture already separates:

- Observations
- Forecasts
- AI
- Replay
- Anomalies

The frontend should mirror those same boundaries.

The state architecture should reflect the application's domain model.

## State Ownership

### Globe Store

Responsible for:

- Camera position
- Zoom level
- Globe rotation
- Selected path
- Selected station
- Active overlays

```typescript
interface GlobeState {
  cameraPosition: CameraPosition;
  selectedPath: string | null;
  enabledLayers: Layer[];
  zoomLevel: number;
}
```

---

### Replay Store

Responsible for:

- Timeline position
- Playback state
- Playback speed
- Replay window

```typescript
interface ReplayState {
  currentTimestamp: Date;
  playbackSpeed: number;
  isPlaying: boolean;
}
```

---

### Forecast Store

Responsible for:

- Forecast results
- Active forecast provider
- Prediction window
- Confidence thresholds

```typescript
interface ForecastState {
  selectedBand: string;
  forecastWindow: number;
  activeProvider: string;
}
```

---

### QSO Story Store

Responsible for:

- Selected contact
- AI narrative
- Supporting evidence
- Similar contacts

```typescript
interface QSOStoryState {
  selectedContact: Contact | null;
  narrative: Narrative | null;
}
```

---

### User Preferences Store

Responsible for:

- Theme selection
- Animation preferences
- Reduced-motion settings
- Saved filters
- Layout preferences

```typescript
interface UserPreferences {
  theme: string;
  reduceMotion: boolean;
  savedFilters: Filter[];
}
```

## State Categories

The application shall distinguish among four categories of state.

### Persistent State

Examples:

- User preferences
- Saved filters
- Local ADIF imports

Storage:

```text
IndexedDB
LocalStorage
```

---

### Session State

Examples:

- Current timeline position
- Selected band
- Open panels

Storage:

```text
In-memory
```

---

### Server State

Examples:

- NOAA observations
- PSK Reporter spots
- Forecasts

Storage:

```text
API cache
Redis
```

---

### Derived State

Examples:

- Band rankings
- Visible paths
- Spot-density calculations
- Active anomalies

Derived state should never be persisted.

---

## State Synchronization Rules

The following interactions shall remain synchronized.

| Action | Required Synchronization |
| --- | --- |
| Selecting a path | Highlight globe + open QSO Story |
| Moving the timeline | Update all replay layers |
| Changing the band | Refresh observations + forecasts |
| Entering replay mode | Freeze live updates |
| Returning to live mode | Restore live observations |

---

## Technology Selection

The application shall use:

```text
React
+
Zustand
```

The application shall avoid:

```text
Redux
MobX
```

unless future requirements justify their introduction.

---

## Performance Requirements

State updates shall remain localized whenever possible.

The application should avoid unnecessary re-rendering.

State updates affecting one domain should not automatically trigger updates in unrelated domains.
