# ADR-010: Standardize Globe Overlays on Three.js

**Status:** Accepted

**Date:** 2026-09-18

---

## Context

ADR-001 selected Three.js as the primary globe-rendering engine and Deck.gl
for overlay rendering.

During Phase 2 implementation, the Radio Weather Globe evolved into a unified
Three.js rendering architecture.

The completed visualization system uses Three.js for both the globe and its
data overlays, including:

- signal paths
- spot density
- solar terminator
- solar weather
- propagation predictions
- anomaly visualization
- station markers

These systems are coordinated by `GlobeRenderingContext`, which owns the
Three.js scene, renderer, camera, navigation controls, visualization layers,
interaction handling, performance monitoring, and animation lifecycle.

Introducing Deck.gl after these capabilities were implemented would require a
second rendering abstraction without currently providing a demonstrated
functional or performance benefit.

The implemented architecture therefore differs from the Deck.gl overlay
portion of ADR-001 and requires the architectural decision record to be
updated.

---

## Decision

Standardize the Radio Weather Globe rendering pipeline on Three.js for both
globe rendering and visualization overlays.

Deck.gl will not be introduced as a Phase 2 rendering dependency.

This decision supersedes only the Deck.gl overlay portion of ADR-001.

ADR-001's decision to use Three.js as the primary globe-rendering engine
remains in effect.

---

## Alternatives Considered

### Three.js Globe with Deck.gl Overlays

This is the architecture originally selected in ADR-001.

**Advantages**

- Deck.gl provides specialized geospatial visualization abstractions.
- It supports high-volume data visualization patterns.
- It offers an established ecosystem of geospatial layers.

**Disadvantages**

- Phase 2 overlay capabilities are already implemented in Three.js.
- It would introduce another rendering abstraction and lifecycle.
- Interaction would need coordination between Three.js and Deck.gl.
- Animation and layer visibility would span multiple rendering systems.
- Resource ownership and disposal would become more complex.
- It would add a dependency without a demonstrated Phase 2 requirement.

---

### Unified Three.js Rendering

Use Three.js for the Earth, atmosphere, stations, paths, environmental
visualizations, predictions, and anomalies.

**Advantages**

- One rendering engine owns the complete scene.
- One animation loop coordinates animated layers.
- Raycasting and selection use one object model.
- Layer visibility is coordinated through one rendering context.
- Three.js resource ownership and disposal remain explicit.
- Existing Phase 2 functionality requires no migration.
- Domain-specific visual behavior can be implemented directly.

**Disadvantages**

- Geospatial visualization behavior requires more custom implementation.
- The project cannot directly use Deck.gl layer abstractions.
- Very large future datasets may require additional optimization or a
  specialized rendering strategy.

---

### Introduce Deck.gl Only for Future High-Volume Layers

Keep the current Three.js implementation and reserve Deck.gl for a future
visualization that demonstrates a concrete need for it.

**Advantages**

- Avoids unnecessary Phase 2 complexity.
- Leaves Deck.gl available as a future architectural option.
- Allows future decisions to be based on measured requirements.

**Disadvantages**

- A future introduction could require integration between two rendering
  systems.
- The rendering architecture could become more complex if both engines must
  coexist.

---

## Rationale

The Phase 2 implementation demonstrates that the required globe overlays can
be implemented within the existing Three.js rendering architecture.

The globe currently benefits from a single rendering lifecycle:

```text
React Application
       |
       v
useGlobeRenderer
       |
       v
GlobeRenderingContext
       |
       +---- Three.js Scene
       |
       +---- Visualization Layers
       |
       +---- Interaction / Raycasting
       |
       +---- Navigation Controls
       |
       +---- Performance Monitoring
       |
       +---- Single Animation Loop
```

Keeping overlays in this architecture avoids introducing coordination between
two rendering engines solely to conform to an earlier implementation plan.

The decision does not reject Deck.gl as a technology. It establishes that a
new rendering dependency should solve a demonstrated problem rather than be
introduced when the existing renderer already satisfies the required
capabilities.

## Consequences

### Positive Consequences

- Globe rendering and overlays share one rendering engine.
- The application maintains one `requestAnimationFrame` lifecycle.
- Layer animation remains centrally coordinated.
- Selection and hover use the same Three.js raycasting system.
- Visualization layers share a consistent visibility model.
- Three.js resource ownership and disposal remain explicit.
- Reduced-motion behavior can be propagated consistently.
- No additional rendering dependency is required for Phase 2.

### Negative Consequences

- Geospatial overlays require custom Three.js implementation.
- The project does not receive Deck.gl's built-in layer abstractions.
- High-volume future visualization requirements may require additional
  optimization.
- ADR-001 no longer describes the complete current rendering architecture
  without reference to this ADR.

## Implementation Notes

No renderer migration is required.

The Phase 2 implementation already follows this decision.

The rendering subsystem includes:

- `GlobeRenderingContext`
- `SignalArcCollection`
- `SpotDensityLayer`
- `SolarTerminatorLayer`
- `SolarWeatherLayer`
- `PredictionPathLayer`
- `AnomalyLayer`
- station-marker rendering
- centralized navigation and interaction
- centralized rendering-performance monitoring

Visualization layers receive application data explicitly rather than
retrieving data themselves.

Animated layers advance through the existing `GlobeRenderingContext` render
loop rather than creating independent animation loops.

Future rendering layers should follow the same architecture unless a later ADR
documents a reason to introduce another rendering engine.

## Performance Considerations

Phase 2 performance validation targets approximately 60 FPS on desktop and
30 FPS on mobile.

Development profiling observed approximately 60 FPS on the desktop
development environment.

Responsive browser profiling also remained approximately 60 FPS. Responsive
browser emulation is not equivalent to physical mobile hardware, so future
performance work should include representative physical-device testing when
mobile performance becomes a release criterion requiring hardware-level
validation.

Deck.gl should be reconsidered only if measured rendering requirements reveal a
problem that the Three.js architecture cannot reasonably address.

Possible review triggers include:

- substantially larger visualization datasets
- unacceptable draw-call growth
- GPU-memory pressure
- geospatial aggregation requirements that duplicate mature Deck.gl behavior
- inability to meet established frame-rate targets after Three.js
  optimization

## Review Triggers

Review this decision if:

- Three.js can no longer meet documented performance targets.
- Overlay data volume grows substantially.
- A new visualization requires capabilities that would be costly to reproduce
  in Three.js.
- Deck.gl or another visualization engine provides a measurable performance or
  maintainability advantage.
- The application moves toward substantially more complex geospatial analysis.

A review trigger does not automatically require a rendering-engine change. It
indicates that the trade-off should be measured again.
