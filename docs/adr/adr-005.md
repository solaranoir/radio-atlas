# ADR-005: Implement a Provider-Agnostic Forecast Architecture

**Status:** Accepted

**Date:** 2026-08-14

**Authors:** SolaraSphere Engineering

---

## Context

Forecasting is one of Radio Atlas's primary differentiators.

Most amateur radio applications focus on historical data and current operating conditions.

Radio Atlas attempts to answer a different question:

> What will happen next?

The application should help operators anticipate:

- Band openings
- Band closures
- Geographic propagation opportunities
- Changes in signal quality
- Gray-line transitions
- Rare DX opportunities

The competitive analysis revealed that existing forecasting approaches vary significantly.

Examples include:

| Forecast Source | Method |
| --- | --- |
| VOACAP | Physical propagation modeling |
| PSK Reporter | Real-time observations |
| WSPR | Signal reporting |
| NOAA | Solar observations |
| Historical analysis | Statistical modeling |
| Machine learning | Predictive modeling |

No single forecasting provider is likely to remain sufficient throughout the life of the project.

---

## Decision

Radio Atlas shall implement a provider-agnostic forecasting architecture.

The application shall separate:

- Forecast generation
- Forecast providers
- Forecast storage
- Forecast visualization

Forecast providers shall be interchangeable.

The user interface shall remain independent of the underlying forecast implementation.

## Alternatives Considered

### Option 1: VOACAP Only

Use VOACAP as the exclusive forecasting provider.

#### Advantages

- Well-established propagation model
- Trusted within the amateur radio community
- Scientifically grounded

#### Disadvantages

- Difficult to extend
- No machine-learning support
- Less responsive to real-time observations

---

### Option 2: Real-Time Trend Analysis Only

Use PSK Reporter and historical observations to generate forecasts.

#### Advantages

- Simpler implementation
- Lower computational cost
- Highly responsive to current conditions

#### Disadvantages

- Limited predictive capability
- Dependent on observation volume
- Reduced scientific modeling

---

### Option 3: Provider-Agnostic Architecture (Selected)

Support multiple forecasting providers through a common interface.

#### Advantages

- Greater flexibility
- Easier experimentation
- Improved testability
- Better long-term maintainability
- Support for future models

#### Disadvantages

- Additional implementation complexity
- More abstraction layers

---

## Rationale

The competitive analysis suggested that forecasting should become a dedicated workspace rather than a simple dashboard widget.

The forecasting system should evolve over time.

Version 1.0 should prioritize:

- Trend analysis
- Historical observations
- Gray-line transitions

Future releases may introduce:

- VOACAP integration
- Machine-learning models
- Ensemble forecasting
- Seasonal models
- Propagation anomaly forecasting

A provider abstraction allows each model to evolve independently.

## Forecast Storage

Forecasts shall be stored separately from observations.

```text
forecasts

├── provider
├── generated_at
├── band
├── confidence
├── probability
└── expiration
```

Expired forecasts may be removed automatically.

Historical forecasts may be retained for replay analysis.

---

## User Interface Requirements

Predicted paths shall always be visually distinguishable from observed paths.

Examples:

| Visualization | Meaning |
| --- | --- |
| Solid line | Observed |
| Dashed line | Predicted |
| Pulsing line | Active |
| Fading line | Closing |
| Flare | Anomalous |

Users shall always understand when they are viewing a prediction rather than an observation.
